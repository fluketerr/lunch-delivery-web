> แยกหน้าแล้ว: `/owner/route` ใช้สร้าง preview และยืนยันเท่านั้น หลังสำเร็จล้างแผน การ์ด สรุป และเส้นทาง กลับเป็นหน้าเริ่มต้น ไม่โหลดใบงานจริงกลับมา ส่วน `/owner/confirmed-jobs` (เมนูใบงานที่ยืนยันแล้ว) โหลดใบงานตามวันที่ พร้อมรายละเอียด สถานะ แมพ และลิงก์ไรเดอร์ โดย `viewingSaved` แยกข้อมูลที่ใช้แสดงของแต่ละหน้า ข้อความอัปเดตก่อนหน้านี้ด้านล่างเป็นประวัติการทำงานก่อนแยกหน้า

> อัปเดตหลังรวม branch ux-ui: ปุ่มยืนยันต่อ `/confirm` แล้ว ส่งเฉพาะ preview_id กันกดซ้ำและตรวจหมดอายุ หลังสำเร็จโหลดรายการกับรายละเอียดจริงกลับมาแสดงด้วย UI เดิม รวมถึงโหลดเส้นทางให้แมพและเลือกการ์ดกรองใบงานได้ ข้อมูลแสดงผลอยู่ใน `displayPlan()` ส่วน `previewPlan()` ใช้เฉพาะแผนก่อนยืนยัน กรณี HTTP 409 ล้างแผนที่ถูกปฏิเสธและกลับไปสร้างใหม่เพื่อไม่ให้กดยืนยันแผนเก่าซ้ำ Build และ tests เฉพาะส่วนนี้ 3 กรณีผ่าน ยังไม่ได้ทดสอบสร้างใบงานกับฐานข้อมูลจริง

## 3. งานหลัก A: วาดแผนที่

### ข้อมูลพร้อมใช้จาก RouteService

```ts
service.previewPlan()    // DeliveryPlan | null
service.jobs()           // PlannedJob[]
service.routeLines()     // PreviewJobRoute[]
service.loadingRoutes()  // boolean
service.routeError()     // string | null
```

`routeLines()` มีรูปแบบนี้:

```ts
[
  {
    jobIndex: 0,
    line: {
      type: 'LineString',
      coordinates: [[103.252125, 16.246063], [103.253, 16.247]],
    },
  },
]
```

พิกัดข้างต้นเป็นเพียงตัวอย่างสำหรับอธิบายรูปแบบข้อมูล

- `jobIndex` เริ่มจาก 0 และอ้างอิง `service.jobs()[jobIndex]` ของ preview ปัจจุบัน ไม่ใช่ `job_id` ในฐานข้อมูล
- พิกัดร้านอยู่ใน `service.previewPlan()?.settings.origin`
- หมุดจุดส่งอ่านจาก `job.stops`: พิกัดอยู่ใน `stop.order.latitude` และ `stop.order.longitude`
- หมายเลขหมุดใช้ `stop.stop_sequence` เริ่ม 1 ใหม่ในแต่ละใบงาน
- GeoJSON ใช้ `[longitude, latitude]` ส่วน `L.marker()` และ `L.polyline()` ใช้ `[latitude, longitude]`; ถ้าใช้ `L.geoJSON(line)` ให้ส่ง GeoJSON เดิมได้เลย

## 4. งานหลัก B: ยืนยันสร้างใบงานจริง

### API ที่ใช้

```http
POST /api/job-sheets/confirm
Content-Type: application/json
```

```json
{ "preview_id": "รหัสจาก preview ปัจจุบัน" }
```

เมื่อสำเร็จตอบ HTTP 201:

```json
{
  "jobs": [
    { "job_id": 101, "job_code": "482731" },
    { "job_id": 102, "job_code": "659214" }
  ]
}
```

เลขข้างต้นเป็นตัวอย่าง `job_code` ใหม่เป็นตัวเลข 6 หลักในรูป string และหนึ่งคำขอยืนยันจะสร้าง **ทุกใบงานใน preview** ไม่ใช่ยืนยันทีละการ์ด

### รายการที่ต้องทำ

- [ ] เพิ่ม interface ผลตอบกลับ confirm เช่น `{ jobs: { job_id: number; job_code: string }[] }`
- [ ] เพิ่มเมธอดเรียก `/confirm` ใน service โดยส่ง `preview_id` ของแผนที่กำลังแสดง ไม่ส่ง jobs/ราคา/ลำดับส่งให้ backend บันทึกจาก frontend
- [ ] เพิ่มเมธอดยืนยันใน `route.ts` และเปลี่ยน `(click)` ของปุ่ม “ยืนยันสร้างใบงาน” ให้เรียกเมธอดนี้
- [ ] เพิ่มสถานะกำลังยืนยัน กันกดซ้ำ และปิดปุ่มคำนวณ/เสนอแผนอื่นระหว่างยืนยัน
- [ ] ตรวจว่ามี preview และยังไม่หมดอายุก่อนส่ง; เมื่อเปลี่ยนแผนต้องใช้ `preview_id` ใหม่เสมอ
- [ ] แสดงเลขใบงานที่ backend สร้างกลับมา ให้เจ้าของร้านส่งต่อเลขแก่ไรเดอร์ได้
- [ ] เปลี่ยน `confirmRoute` หลัง API สำเร็จเท่านั้น การ toggle signal นี้อย่างเดียวไม่ได้บันทึกฐานข้อมูล
- [ ] เมื่อสำเร็จ ล้าง preview เส้นทาง ข้อมูลแผนก่อนหน้า และข้อความเดิม แล้วโหลดรายการใบงานที่สร้างจริง
- [ ] รีเฟรช eligible orders เพื่อไม่แสดงออเดอร์ที่จัดงานแล้วเป็นรายการว่างอีก
- [ ] ถ้า HTTP 409 ให้แสดงข้อความจาก backend เช่นแผนหมดอายุ/ออเดอร์เปลี่ยน/ถูกจัดงานแล้ว และให้คำนวณใหม่
- [ ] ถ้าเครือข่ายขาดหลังส่ง confirm อย่าสรุปทันทีว่าไม่ได้สร้าง: โหลดรายการใบงานเพื่อตรวจผล เพราะ server อาจบันทึกสำเร็จแต่ response กลับไม่ถึง
- [ ] อย่าล้างแผนก่อนทราบผลยืนยัน และอย่าสร้างใบงานใหม่อัตโนมัติเมื่อเกิด error

Backend ตรวจแผนเดิม ล็อกและตรวจออเดอร์ แล้วบันทึก `job_sheets` และ `job_stops` ภายใน transaction พร้อมสร้าง `job_code` จึงไม่ต้องเขียน SQL จาก frontend

## 5. งานหลัก C: แสดงและเปิดใบงานที่บันทึกแล้ว

- [ ] โหลดรายการจริงด้วย `GET /api/job-sheets?date=YYYY-MM-DD` แยกจากการ์ด preview
- [ ] แสดง `job_code` และข้อมูลจริงแทน `jobsReady` / ตัวอย่างสถานะใน `route.ts`
- [ ] ใช้ `job_id` หรือ `job_code` ติดตามใบงานหลังบันทึก ไม่ใช้ลำดับการ์ด preview เป็นรหัสถาวร
- [ ] เปิดรายละเอียดได้ผ่าน `GET /api/job-sheets/by-code/:code`
- [ ] ถ้าจะวาดเส้นของใบงานที่บันทึกแล้ว ให้ขอ `/route` จาก settings และ stops ของใบงานนั้นอีกครั้ง เพราะข้อมูลเส้น preview ถูกล้างได้
- [ ] ทดสอบส่งต่อเลขใบงานเข้าหน้า `/rider/:workNumber`
- [ ] ทดสอบเริ่มงานและส่งจุดต่าง ๆ แล้วโหลดข้อมูลจริงกลับมาตรวจ โดยฝั่งไรเดอร์มี API service และโค้ดเชื่อมแล้ว ไม่ต้องเริ่มเขียนใหม่ทั้งหมด

API ฝั่งไรเดอร์ที่มีแล้ว:

| การทำงาน | API |
|---|---|
| เปิดใบงาน | `GET /api/job-sheets/by-code/:code` |
| เริ่มงาน | `POST /api/job-sheets/by-code/:code/start` พร้อม body `{}` |
| ส่งสำเร็จแต่ละจุด | `POST /api/job-sheets/by-code/:code/stops/:stopId/deliver` พร้อม body `{}` |

ใช้ `stop_id` ที่ backend คืนให้ใน API ส่งสำเร็จ ไม่ใช้ `stop_sequence` หรือ `order_id` แทน

## 6. เวลา สถานะ และข้อจำกัดที่ต้องทราบ

### อายุของ preview

- Backend เก็บ preview ใน RAM ของโปรเซส ไม่ใช่ตารางฐานข้อมูล มีอายุ 30 นาที และเก็บสูงสุด 50 แผนต่อโปรเซส
- หมดอายุแล้ว confirm ไม่ผ่าน แผนที่หมดอายุถูกล้างเมื่อมีการสร้าง preview ใหม่; ถ้าเต็มจะลบแผนที่เข้ามาก่อน และยืนยันสำเร็จก็ลบแผนที่ใช้แล้ว
- Backend restart หรือแผนถูกนำออกจาก cache ก็ต้องคำนวณใหม่ แม้หน้าเว็บยังแสดงแผนเก่า
- Preview และ confirm ต้องเข้าถึง backend โปรเซสเดียวกัน หากภายหลังรันหลาย instance ต้องปรับที่เก็บ preview ให้ใช้ร่วมกัน
- Frontend เก็บข้อมูลใน service ชั่วคราว ไม่ได้ทำให้ preview มีอายุเพิ่มขึ้น

### การใช้ expires_at

`expires_at` เป็น ISO string แบบ UTC ที่ลงท้าย `Z` เก็บค่าเดิมไว้ เปรียบเทียบได้ด้วย:

```ts
const expired = Date.now() >= new Date(preview.expires_at).getTime();
```

ถ้าจะแสดงเวลาไทย:

```ts
new Date(preview.expires_at).toLocaleString('th-TH', {
  timeZone: 'Asia/Bangkok',
});
```

- [ ] แสดงเวลาหมดอายุและแจ้งให้คำนวณใหม่เมื่อหมดเวลา
- [ ] เช็กหมดอายุตอนกดยืนยันทุกครั้ง; ถ้าต้องการให้ปุ่มเปลี่ยนเองตามเวลา ต้องมีตัวอัปเดตเวลา ไม่ใช้ `computed(() => Date.now())` เพียงอย่างเดียว เพราะเวลาจริงไม่ใช่ signal

เวลานี้เป็นอายุของแผน ไม่ใช่เวลาจัดส่ง ส่วนเวลาส่งอ้างอิง `settings.departure_time` / `deadline_time` และเวลาถึงของแต่ละ stop

### ข้อมูลและ error ก่อนเดโม่

- [ ] แสดง error ตอนดึง eligible orders และคำนวณ preview ครั้งแรก ปัจจุบันสองส่วนนี้ยัง log ลง console เป็นหลัก
- [ ] แสดงสถานะไม่มีออเดอร์ โดยไม่ส่ง `order_ids: []` ไปคำนวณ
- [ ] รองรับกรณีมีเกิน 30 ออเดอร์: backend รับ 1–30 รายการต่อคำขอ ปัจจุบัน frontend ส่งออเดอร์ที่พร้อมทั้งหมด
- [ ] แก้การเลือกวันนี้ให้เป็นวันที่ไทย ปัจจุบัน `toISOString().split('T')[0]` ใช้วันที่ UTC ซึ่งอาจคลาดเคลื่อนช่วงก่อน 07:00 น. ในไทย
- [ ] ทดสอบข้อมูลจำลองที่อยู่ในพื้นที่บริการ: ตัวสุ่มยังอ่านลูกค้าทั้งหมด อาจสุ่มลูกค้านอกพื้นที่จน preview ตอบ 422
- [ ] แสดง `error.details` ที่ backend คืนเมื่อพิกัด/ข้อมูลออเดอร์ไม่ถูกต้อง เพื่อบอกว่าออเดอร์ใดต้องแก้
- [ ] ถ้าต้องการภาพรวมเวลาทั้งแผน ให้แสดงเวลาของแต่ละใบงานหรือเวลาที่ใบงานสุดท้ายจะเสร็จ โดยไม่บวกระยะเวลาของไรเดอร์ทุกคนเป็นเวลารอรวม เพราะออกส่งพร้อมกัน

### เงื่อนไขคำนวณที่มีแล้ว

| เรื่อง | พฤติกรรมปัจจุบัน |
|---|---|
| จำนวนออเดอร์ต่อใบงาน | ไม่เกิน 3 ออเดอร์; แต่ละออเดอร์มี 1–3 กล่อง |
| พื้นที่บริการ | ระยะทางถนนจากร้านถึงลูกค้าแต่ละรายไม่เกิน 3 กม. ไม่ใช่ระยะรวมต่อใบงานต้องไม่เกิน 3 กม. |
| ค่าจัดส่งต่อใบงาน | ค่าเริ่มต้น `15 + (2 × จำนวนกล่องในใบงาน × ระยะทางรวมของใบงาน)` |
| เวลา | ระยะทาง ÷ ความเร็ว 30 กม./ชม. และเพิ่มเวลาส่งมอบ 2 นาทีต่อออเดอร์; ตรวจส่งมอบเสร็จภายใน 12:30 จากการออก 11:30 |
| ราคาอาหาร | คำนวณจาก unit_price/unit_cost ของออเดอร์; ข้อมูลจำลองใช้ขาย 65 ต้นทุน 40 บาท |
| เส้นทาง | OSRM driving ไม่ใช่ profile มอเตอร์ไซค์โดยเฉพาะ |
| การเลือกแผน | Greedy รวมเพื่อนใกล้เคียงเมื่อค่าส่งคุ้มกว่าแยกและส่งทัน ไม่รับประกันต้นทุนต่ำที่สุดหรือกำไรทุกชุดข้อมูล |
| ขอแผนอื่น | ส่ง previous_preview_id ข้ามเฉพาะแผนปัจจุบัน; ลองไม่เกิน 10 ครั้งต่อคำขอ แต่กดใหม่ได้เรื่อย ๆ |

อย่าแสดงข้อความรับประกันว่าระบบทำกำไรหรือหาเส้นทางดีที่สุดเสมอ ให้แสดงตัวเลขที่คำนวณได้เพื่อให้เจ้าของร้านตัดสินใจ

## 7. การเชื่อมต่อและรายการตรวจรับ

Frontend ใช้ `/api/job-sheets/...` ผ่าน Angular proxy ส่วน backend โดยตรงใช้ `/job-sheets/...` ไม่มี `/api` นำหน้า

ณ วันที่เขียน [proxy.conf.json](../../proxy.conf.json) ชี้ไป backend บน Render จึงต้องตรวจให้ตรงกับ backend ที่เพื่อนกำลังทดสอบ อย่าคิดว่าการแก้ backend ในเครื่องเปลี่ยน API บน Render แล้ว และหลังแก้ proxy ให้ restart Angular dev server

ลำดับที่แนะนำ: **ทำแมพ → ต่อ confirm → แสดงเลขและรายการใบงานจริง → ทดสอบฝั่งไรเดอร์ → เก็บ error/วันเวลา**

- [ ] สร้าง preview แล้วเห็นการ์ด summary เส้น และหมุดครบ ตำแหน่ง/สี/ลำดับตรงกัน
- [ ] กดขอแผนอื่นแล้วข้อมูลบนการ์ด summary และแมพเปลี่ยนเป็นชุดเดียวกัน ไม่มีเส้นเก่าค้าง
- [ ] ถ้าไม่มีแผนอื่น ยังเห็นแผนเดิมและข้อความอธิบาย
- [ ] โหลดเส้นทางล้มเหลวแล้วแจ้งผู้ใช้และลองใหม่ได้ ไม่แสดงเส้นทางที่ได้มาเพียงบางใบงาน
- [ ] เปลี่ยนหน้าแล้วกลับมายังเห็นข้อมูลเดิมและสร้างแมพได้; รีเฟรชแล้วมีสถานะเริ่มต้นที่เข้าใจได้
- [ ] ยืนยันแล้วได้ job_code จริงครบทุกใบงาน และจำนวนข้อมูลในฐานข้อมูลตรงกับแผน
- [ ] กดซ้ำระหว่างยืนยันไม่สร้างคำขอเพิ่ม และการยืนยันรหัสเดิมหลังสำเร็จไม่สร้างใบงานซ้ำ
- [ ] แผนหมดอายุ/backend restart/ออเดอร์เปลี่ยนแล้วแจ้งให้คำนวณใหม่ได้
- [ ] เปิดเลขใบงานในหน้าไรเดอร์ เห็นจำนวนกล่องและจุดส่งถูกต้อง เริ่มงานและส่งตามลำดับได้
- [ ] ส่งครบแล้วโหลดหน้าขึ้นใหม่ สถานะที่บันทึกยังอยู่
- [ ] ตรวจทั้งหน้าจอคอมพิวเตอร์และมือถือ โดย sidebar/summary ไม่บังปุ่มหรือหมุดสำคัญ

ทดสอบยืนยันและส่งงานกับฐานข้อมูลทดสอบหรือชุดออเดอร์ที่ทีมเตรียมไว้ เพราะขั้นตอนเหล่านี้บันทึกข้อมูลจริง

เอกสารนี้จัดทำจากการอ่านโค้ดปัจจุบัน การทดสอบ API จำลอง/build ที่ผ่านก่อนหน้านี้ไม่ได้แทนการตรวจ flow ทั้งหมดกับ backend ที่ deploy และฐานข้อมูลจริงหลังเพื่อนต่อ UI เสร็จ
